# 智能报销平台 7 天加速完结计划

制定日期：2026-09-13

## 目标

在当前登录、报销、审批、通知、幂等和附件基础代码之上，用 7 个学习日完成以下增强项：

- RabbitMQ 异步通知。
- MinIO 对象存储。
- AI 发票识别。
- 前后端完整业务闭环。
- Docker Compose 可部署演示环境。
- 测试、文档和项目讲解材料。

这里的“完结”指项目能够运行、演示、测试和讲清设计思路，不追求生产级集群、高并发优化和复杂分布式架构。

## 加速学习原则

### 1. 只学习当前功能必需的原理

每个模块先掌握一条核心调用链，再开始编码，不进行与当前任务无关的源码深挖。

```text
理解主流程
→ 跟敲核心代码
→ 编译和小范围测试
→ 完成一次真实联调
→ 记录能复述的原理
```

### 2. 非核心代码直接搭好

配置类、DTO、VO、Controller、基础异常处理、测试骨架和重复样板代码可以直接生成并添加中文注释。

用户重点跟敲并理解：

- 业务权限判断。
- 状态转换。
- 数据一致性。
- 幂等与重复消费处理。
- 文件安全。
- AI 结果校验和人工确认。

### 3. 每个模块只保留一个主要实现

- RabbitMQ 只实现一条审批事件通知链路，再复用到其他事件。
- MinIO 只实现上传、读取和删除，不做复杂生命周期策略。
- AI 只接入一个识别客户端，不同时比较多个模型。
- 部署只使用一套 Docker Compose，不引入 Kubernetes。

### 4. 先完成闭环，再增加质量

每个功能按照以下顺序推进：

```text
成功路径
→ 权限和参数错误
→ 重复请求与失败处理
→ 自动化测试
→ 代码整理
```

不能因为追求一次写出生产级代码而阻塞可运行版本。

### 5. 外部服务失败不能破坏核心报销流程

- RabbitMQ 暂时不可用时，不得破坏已经提交成功的报销业务。
- MinIO 异常时，必须返回明确错误，不能写入虚假的附件记录。
- AI 超时或返回非法数据时，用户仍可以手工填写发票信息。
- AI 建议必须经过用户确认，不能直接修改正式金额。

### 6. 每天只保留一个可验收目标

每天结束前必须至少完成：

- 一条可以运行的业务链路。
- 一次成功场景验证。
- 一次失败或越权场景验证。
- 一段当天学习日志。

如果遇到环境问题，先记录并使用最小替代方案，不能让单个依赖拖住整个项目。

## 7 天执行计划

### Day 19：附件模块完结

目标：完成附件上传、列表、下载和前端展示闭环。

- 整理附件列表查询代码。
- 实现本地附件读取和下载接口。
- 实现仅限可编辑报销单的附件删除。
- 前端增加上传、附件列表、下载和删除操作。
- 验证磁盘文件与数据库元数据一致。

验收：员工可以管理自己草稿或驳回报销单的附件，不能访问其他用户附件。

### Day 20：RabbitMQ 异步通知

核心调用链：

```text
报销业务事务成功
→ 发布审批事件
→ RabbitMQ Exchange
→ Queue
→ Consumer
→ notification 表
```

执行任务：

- 配置 Exchange、Queue、Binding 和 Routing Key。
- 定义审批事件 DTO。
- 编写生产者和消费者。
- 使用稳定的 `messageKey` 防止重复消费。
- 配置有限次数重试并记录最终失败。

验收：同一事件重复投递两次，同一用户只产生一条通知。

### Day 21：MinIO 对象存储

核心设计：

```text
AttachmentStorage
├── LocalFileAttachmentStorage
└── MinioAttachmentStorage
```

执行任务：

- 添加 MinIO 客户端和配置。
- 实现文件上传、读取和删除。
- 继续使用安全 `objectKey` 和 SHA-256 去重。
- 通过配置选择本地存储或 MinIO。
- 保持 `AttachmentService` 不依赖具体存储产品。

验收：切换存储实现后，Controller 和核心附件业务不需要整体重写。

### Day 22：AI 发票识别后端

核心调用链：

```text
上传发票
→ AI 识别适配器
→ 结构化 JSON
→ 后端字段校验
→ 保存识别建议
→ 等待用户确认
```

执行任务：

- 定义 `InvoiceRecognitionClient` 接口。
- 定义结构化识别结果 DTO。
- 实现一个多模态模型适配器。
- 设置超时、有限重试和 JSON 校验。
- 将识别结果保存为建议状态，不直接覆盖正式金额。

验收：AI 返回错误或超时时，报销单仍可手工编辑。

### Day 23：AI 前端与人工确认

- 上传发票后允许触发识别。
- 展示发票号码、日期、金额、商户和置信度。
- 用户可以修改识别结果。
- 只有点击确认后才写入正式字段。
- AI 不可用时显示手工填写入口。

验收：AI 只提供建议，最终数据由用户确认。

### Day 24：可部署演示环境

使用 Docker Compose 编排：

```text
Vue / Nginx
Spring Boot
MySQL
Redis
RabbitMQ
MinIO
```

执行任务：

- 创建前后端 Dockerfile。
- 配置 Nginx 静态资源和 `/api` 反向代理。
- 使用环境变量提供数据库、JWT、消息队列和对象存储配置。
- 配置数据卷和健康检查。
- 禁止把真实密钥写入 Git。

验收：在新环境中通过一条 Compose 命令启动全部服务，并完成健康检查。

### Day 25：总回归与项目完结

- 修复旧测试中的接口签名和构造器依赖。
- 执行完整 Maven 测试。
- 执行前端 TypeScript 检查和生产构建。
- 回归登录、报销、审批、通知、附件和 AI 流程。
- 更新 README、API 文档和数据字典。
- 清理临时测试数据、过期 TODO 和无效配置。
- 整理一套完整演示步骤和面试讲解。

验收：项目可启动、可演示、可测试，并能够解释关键技术选择。

## 每日合作方式

每个任务使用同一节奏：

1. 先说明今天唯一的验收目标。
2. 用简图讲清请求调用链和数据流。
3. 补齐非核心代码和中文注释。
4. 用户跟敲关键业务代码。
5. 检查代码，指出具体问题和原因。
6. 执行编译、小范围测试和一次真实联调。
7. 清理过期 TODO，写当天日志和下一日计划。

## 时间预估

- 每天 4～6 小时：约 7 个学习日。
- 每天 2～3 小时：约 10～12 个学习日。
- Docker、RabbitMQ、MinIO 或外部 AI 接口出现环境问题时，额外预留 1～2 天。

## 明确不做的内容

为了按期完结，本阶段不实现：

- Kubernetes 和多节点集群。
- RabbitMQ 高可用集群和复杂死信治理平台。
- MinIO 分布式部署和生命周期归档策略。
- 多模型路由与大规模 AI 评测。
- 微服务拆分和分布式事务框架。
- 复杂财务对账和企业级工作流引擎。

这些内容可以在项目 MVP 完结后作为第二阶段增强。
