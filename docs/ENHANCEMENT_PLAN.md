# 后续增强项业务规划

基础报销、审批、付款和审计链路已经完成。后续增强功能按“先保证正确性，再引入基础设施”的顺序推进。

## 1. 失败日志独立事务

### 业务目标

业务失败时，即使业务事务回滚，也必须保留 `FAILURE` 审计记录。

### 实现思路

新增独立写入服务方法，使用 `@Transactional(propagation = REQUIRES_NEW)`：

```text
业务方法开始
  -> 执行业务更新
  -> 成功：写 SUCCESS
  -> 异常：独立事务写 FAILURE
  -> 重新抛出原始异常
```

验收：制造一次状态冲突，报销单更新回滚，但操作日志表仍有一条 FAILURE。

## 2. Redis 幂等与提交防重复

### 业务目标

同一用户重复点击提交或重复发送审批请求，只处理一次。

### 数据与接口

- 请求头：`Idempotency-Key`
- Redis Key：`idempotency:{userId}:{key}`
- Value：业务类型、业务 ID、处理状态和响应摘要
- 过期时间：建议 10 分钟

### 服务流程

1. Controller 读取 `Idempotency-Key`。
2. Service 使用 Redis `SET NX EX` 抢占请求。
3. 抢占失败则返回上一次处理结果或 409。
4. 业务成功后保存完成结果。
5. 业务异常后释放处理中标记，允许安全重试。

验收：同一 key 连续请求两次，只创建一条审批任务。

## 3. RabbitMQ 审批通知

### 业务目标

审批通过、驳回、付款完成后，向申请人发送站内通知，主业务不依赖通知服务可用。

### 事件设计

- Exchange：`expense.events`
- Routing Key：`report.approved`、`report.rejected`、`report.paid`
- 消息唯一键：`messageKey = eventType + ':' + reportId + ':' + approvalRound`

### 服务流程

1. 审批事务成功后发布领域事件。
2. 消费者接收事件并按 `messageKey` 去重。
3. 写入 `notification` 表。
4. 失败时重试，超过次数进入死信队列。

验收：同一消息投递两次，申请人只收到一条通知。

## 4. MinIO 发票附件

### 业务目标

支持上传发票附件，并通过哈希避免重复文件。

### 数据与接口

- `POST /api/reports/{id}/attachments`
- 保存对象 key、原始文件名、大小、Content-Type、SHA-256
- 数据库唯一约束：`(report_id, sha256)`

### 服务流程

1. 校验登录用户是否有权修改报销单。
2. 限制文件大小和类型。
3. 计算 SHA-256。
4. 哈希已存在则复用已有对象。
5. 上传 MinIO 并保存附件元数据。

验收：同一文件重复上传不会产生两份对象或两条元数据。

## 5. AI 发票识别适配器

### 业务目标

AI 只负责提供识别建议，不能直接修改已提交报销单，也不能阻塞手工录入。

### 设计边界

- 定义 `InvoiceRecognitionClient` 接口。
- 返回结构化 JSON：发票号码、日期、金额、税额、商户、置信度。
- 超时、重试和 JSON 校验由适配层负责。
- 低置信度结果进入人工确认状态。
- AI 不可用时允许用户手工填写。

验收：AI 服务超时后，页面仍可手工保存明细；确认前不写入正式金额。

## 推荐开发顺序

1. 失败日志独立事务
2. Redis 幂等
3. RabbitMQ 通知
4. MinIO 附件
5. AI 发票识别

每项增强功能都应同时补充：数据库变更、Service 单元测试、接口测试、失败场景和文档更新。
